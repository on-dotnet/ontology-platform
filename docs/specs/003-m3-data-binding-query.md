## 1 用户能做什么

1. **连接数据库**：管理员新建 PostgreSQL 数据源，测试连接，读取目录（模式、表、视图、列、类型、注释、主外键）。平台对数据源只读，口令保存后不再显示。
2. **把本体绑定到数据**：对象类型绑定到表或视图（加主键列），属性绑定到列，关系绑定到外键或连接表。可以让 AI 根据目录给出建议，也可以手工编辑；两种方式都生成变更集，审核合并并发布后才生效。
3. **按本体浏览对象**：在"探索"页按对象类型列出数据（筛选、排序、翻页），打开一个对象看它的属性，沿关系走到相关对象。每个对象都标明来自哪个数据源、哪张表、哪个主键。
4. **让外部智能体使用本体**：用户创建访问令牌，外部智能体经 MCP 列出本体，搜索与读取类型、属性、关系、术语，按本体查对象；有相应权限的令牌还可以提议变更，提议进入审核页。

验收（路线图）：**PG 中的冶金样例数据可按本体查询**。具体是在开发栈上走通下面这条线，其中界面部分需要用户登录后才能走查，自动化验收以第 15 节的测试为准：

装载冶金样例库（第 11 节）→ 新建数据源并测试 → 读取目录 → AI 建议绑定 → 审核合并 → 发布 → 在探索页列出炉次，按厂区筛选，打开一个炉次，沿"对应浇次 → 产出板坯 → 参与轧制 → 产出钢卷"逐跳走到钢卷，再按重量给钢卷排序，每一步都显示来源 → 用访问令牌经 MCP 做同样的查询。

这条路线只用钢铁样例本体（`samples/steel/ontology.ttl`）里已有的元素：五个对象类型、四个关系，以及 `externalId`、`organizationId`、`siteId`、`weight` 四个属性。自动化测试导入的就是这份本体（测试镜像里的副本在 `backend/tests/fixtures/ontology/samples`）。开发栈上由资料识别出来的本体属性更多，走查时可以多绑几列，但验收不依赖它。

## 4 访问令牌与 Bearer 认证

现在只有 Cookie 会话加 CSRF，外部智能体用不了。M3 新增个人访问令牌。

**令牌**：
- 格式：`op_pat_` 加 43 个 URL 安全字符（`secrets.token_urlsafe(32)`，256 位随机）。固定前缀便于密钥扫描工具识别（正则 `op_pat_[A-Za-z0-9_-]{43}`）。
- 只在创建成功的那一次响应里返回全文；库里只存 SHA-256（随机量足够，不需要慢哈希，与会话令牌同一做法）和前 15 个字符（`op_pat_` 加 8 位，用于在列表里辨认）。
- 每个令牌有名称、作用域、过期时间（必填，1–365 天，默认 90 天），可撤销。每个用户最多 10 个未过期、未撤销的令牌。
- 表 `identity.access_tokens`（迁移 v0007）：`id`、`user_id`、`name`、`token_prefix`、`token_hash`（唯一）、`scopes`（jsonb）、`created_at`、`expires_at`、`last_used_at`、`last_used_ip`、`revoked_at`、`revoked_by`、`last_rejected_at`。

**作用域**：

| 作用域 | 允许 | 创建时要求的角色 |
|---|---|---|
| `ontology:read` | 读取已发布的本体（MCP 的本体类工具、`/api` 的版本读取与导出） | 任何角色 |
| `objects:read` | 按本体查对象（MCP 的对象类工具、`/api` 的对象查询） | 任何角色 |
| `changes:propose` | 经 MCP 提议变更 | editor、reviewer、admin |

令牌的权限是"主人的角色"与"令牌的作用域"的交集，每次请求都按主人当时的角色重新判断：主人被降级或停用后，令牌立刻随之失效或降权。

**使用**：
- 请求头 `Authorization: Bearer <令牌>`。带这个头的请求只按令牌认证，不再看 Cookie；令牌无效时返回 401 `auth.invalid_token`，不回退到 Cookie。
- 用令牌的请求不走 CSRF 校验：浏览器不会自动带上 `Authorization` 头，CSRF 的前提不存在。
- 每次请求都查库（按哈希），不缓存，所以撤销、过期、主人停用都立刻生效。`last_used_at` 至多每分钟更新一次。
- **默认拒绝**：`/api` 的路由默认不接受令牌，令牌请求返回 403 `auth.token_not_allowed`；只有显式声明了作用域（依赖 `require_scope(...)`）的路由才接受。M3 声明的路由见接口附录，只有三类：当前用户、已发布版本的读取与导出、对象查询；读工作版本的接口（本体列表、元素、变更集等）都不接受令牌。`/api` 上没有任何写接口接受令牌，令牌唯一的写入口是 MCP 的"提议变更"工具。理由：令牌是给外部程序用的，暴露面要一条一条地开。
- 令牌不能用来管理令牌、数据源、审核和发布。

**管理**：`GET/POST /api/auth/tokens`、`DELETE /api/auth/tokens/{id}`，只能经 Cookie 会话调用。用户管理自己的令牌；admin 可以查看全部令牌（不含全文和哈希）并撤销任何一个。

**审计**：`token.created`、`token.revoked` 每次都记；已知令牌因过期、撤销或主人停用被拒时记 `token.rejected`（同一令牌 10 分钟内只记一条，用 `last_rejected_at` 判断）；令牌的使用按第 13 节记录。审计里只出现令牌 id 和前缀，不出现全文和哈希。

**与 MCP 规范的差距**：规范的授权部分是可选的；实现它的服务端要作为 OAuth 2.1 资源服务器，提供受保护资源元数据（RFC 9728）并校验令牌的受众（RFC 8707）。M3 不实现这一部分，用的是规范之外的静态 Bearer 令牌：只支持 OAuth 流程的 MCP 客户端连不上，能自定义请求头的客户端可以。完整的 OAuth 2.1 授权服务器与企业 OIDC 一起放 M5，届时访问令牌保留给脚本使用。

## 5 数据源与连接器（`connectors` 模块）

### 5.1 连接器接口

接口只有四件事，全部只读；没有任何方法接受 SQL 文本：

| 方法 | 作用 |
|---|---|
| `test()` | 连接、认证、读服务端版本，检查账号是否有写权限（只读地查权限函数） |
| `catalog(schemas)` | 目录发现：模式、表、视图、列、类型、注释、主键、外键 |
| `select(query, limits)` | 执行一条由结构化的 `SelectQuery` 渲染出的 SELECT |
| `cancel()` | 取消正在执行的语句并关闭连接 |

`SelectQuery` 是冻结的数据类：一张主表、可选的一个内连接、要取的列、条件（列、运算符枚举、值）、排序、行数上限。它的字段都是结构化的值，没有"原始片段"这样的字段。

语句由 SQLAlchemy Core 生成（`table()`、`column()`、绑定参数），标识符的引用和分页写法交给方言；目录发现用 SQLAlchemy 的 Inspector。这样以后加 Oracle、Doris、TDengine 时，生成与目录两部分不用重写（[ADR 0002](../adr/0002-tech-stack.md) 的"只实现一次"）。M3 只实现 PostgreSQL，驱动用已有的 psycopg 3，不新增驱动依赖。

### 5.2 数据源

表 `connectors.data_sources`（迁移 v0008）：`id`、`name`（唯一）、`kind`（M3 只有 `postgresql`）、`host`、`port`、`database`、`username`、`ssl_mode`、`schemas`（jsonb，可选的模式范围）、`secret`（密文）、`secret_key_id`、`credential_updated_at`、`allow_samples`（默认否）、`status`（`active` / `archived`）、最近一次测试的时间与结果码、目录状态与刷新时间、`revision`、`created_by`、时间戳。

- **不能指向平台自己的库**：否则会话、令牌哈希、凭据密文都能被绑定出去。保存和测试时先比地址与库名；连接器每次建立连接后（测试、读目录、读样本、查询都一样）再只读地比对两边的数据库系统标识与库名，这样换成 IP 或别名、保存后不测试直接用，都绕不过去。相同就拒绝（422 `datasource.platform_database`）。同一个实例里的另一个库（开发用的样例库就是这样）不受影响。取系统标识的具体查询由批次 3 核实；取不到时只按地址与库名判断，并在 PR 里写明。
- **归档代替删除**：归档时立刻清除密文，行保留，旧版本的绑定仍能显示数据源名称。工作版本或当前生效版本的绑定还在引用它时拒绝归档（409 `datasource.in_use`）。
- **模块依赖只有一个方向**：`ontology` 调用 `connectors`（校验绑定时取数据源摘要和目录里的表）。`connectors` 需要知道"哪些表被哪个对象类型绑定了"（归档检查、列表里的已绑定数），但不反过来导入 `ontology`：它定义一个"用量提供者"的函数类型，由 `main.py` 和 `worker.py` 把 `ontology` 的实现登记进去，做法同 `documents` 的 `register_extractor`。没有登记提供者时，归档一律拒绝（不能当作"没有被引用"），已绑定数显示为未知。
- **修改**带 `revision`，不一致返回 409 `datasource.stale`。改了主机、端口、库、用户名、口令之一，测试结果清空。
- **未保存参数的连接测试**只有 admin 能用，因为它能让平台去连任意地址。

### 5.3 只读（红线）

两道独立的防线，任何一道单独失效都不会写进用户的库：

**第一道，平台只发自己生成的 SELECT。**
- 查询来自已发布的绑定（第 7 节），目录发现来自 Inspector，样本读取（第 5.6 节）也是一条 `SelectQuery`。没有接口、MCP 工具或模型输出能带入 SQL 片段；用户给的筛选值只作绑定参数，运算符取自固定枚举，标识符只来自审核过的绑定并由方言加引号。
- 只有 `connectors` 模块可以导入数据库驱动、建立外部连接和写 SQL 文本；`query`、`mcp`、`ai` 的绑定建议都只能调用 `connectors` 的服务接口。由一条扫描源码的测试守住（做法同 `test_module_boundaries.py`）。

**第二道，连接层。**
- 每个连接都以只读方式打开：会话参数 `default_transaction_read_only=on`，语句在显式的 `READ ONLY` 事务里执行。
- 语句超时（`statement_timeout`，默认 15 秒，`OP_QUERY_TIMEOUT_SECONDS`）、锁等待超时 2 秒、连接超时 5 秒、事务空闲超时。
- 行数上限：语句带 `LIMIT`，读取时再按上限截断，不使用"全部取回"；单条语句最多 `OP_QUERY_MAX_ROWS` 行（默认 1,000）。文本值超过 2,000 字符时截断并标记。
- 可取消：请求被取消（客户端断开、界面点"取消"）或超时，就向数据库发取消并关闭连接。uvicorn 下客户端断开不会自动取消处理函数，所以查询接口要自己监听断开事件（`http.disconnect`）再取消；测试用 `pg_stat_activity` 断言语句确实不在了。
- 每个进程里每个数据源同时最多 4 条语句（api 与 worker 各算各的），排队超过 5 秒返回 503 `query.busy`。M3 每次操作新建连接，不引入连接池依赖。

**另外的提醒**：连接测试发现账号有写权限时，结果里带 `account_can_write`，界面用黄色 ! 提示"建议换用只读账号"。这不是防线，只是提醒。

### 5.4 凭据（红线）

- **加密**：AES-256-GCM。密钥由 `OP_SECRET_KEY` 经 HKDF-SHA256 派生（`info` 为 `op/datasource-credentials/v1`）；每次加密用新的 12 字节随机数；附加认证数据是数据源 id，密文换到别的行解不开。明文是 `{"password": "…"}` 的 JSON，留出以后加客户端证书的余地。
- **存储**：`secret` 列存"版本字节 + 随机数 + 密文与标签"；`secret_key_id` 存派生密钥的指纹（SHA-256 的前 16 个十六进制字符），用来判断是哪把密钥加密的。
- **不回显**：
  - 接口模型里口令是 `SecretStr`，响应里只有 `hasCredential` 和 `credentialUpdatedAt`；修改数据源时不带口令表示不改。
  - 解密只发生在 `connectors/secrets.py`，在建立连接前一刻。
  - 连接和查询的错误只映射成稳定的错误码，加异常类名和 SQLSTATE；驱动的原始报错（可能带主机、用户名、连接串）不进响应、日志、审计和任务表。做法同 `ModelGateway` 对代理地址的处理：在连接器里把驱动异常换成自己的异常并断开异常链（`raise … from None`），引擎设 `hide_parameters=True`。这一步必须在连接器里做完，因为任务执行器会把异常链打进日志、把异常文本存进任务表。
  - 422 的校验错误本来就不回显输入值（`errors.py`）。
- **密钥轮换**：
  1. 把旧值放进 `OP_SECRET_KEY_PREVIOUS`（可以有多个，逗号分隔），新值放进 `OP_SECRET_KEY`，重启。解密时按 `secret_key_id` 选密钥，新写入一律用新密钥。
  2. 在 api 容器里运行 `python -m ontology_platform.modules.connectors.rekey`，把全部凭据用新密钥重新加密。输出只有条数。
  3. 去掉 `OP_SECRET_KEY_PREVIOUS`，重启。
- **密钥丢失**：凭据解不开时，数据源显示"需要重新填写口令"（`datasource.credential_unreadable`），其余功能不受影响。数据库备份里只有密文，密钥要另外保管。
- **依赖**：`cryptography`（Apache-2.0 或 BSD-3-Clause 双许可，来源 PyPI，PyCA 维护）。2026-11-24 在 Docker 主机的临时容器里实测 50.0.2 版：这台主机的 CPU 没有 SSE4.2、AVX、AES 指令，HKDF 与 AES-GCM 的加解密正常。新增的传递依赖只有它自己（`cffi`、`pycparser` 已随 `argon2-cffi` 在锁文件里）。

### 5.5 目录

- 目录发现的结果缓存在 `connectors.catalog_tables`（迁移 v0008）：数据源、模式、表名、种类（表、视图、物化视图、外部表）、注释、列（名称、源类型、类型族、可空、注释、位置）、主键、外键、刷新时间。
- "读取目录"是后台任务 `connectors.refresh_catalog`：成功后在一个事务里整体替换该数据源的缓存。上限 5,000 张表、200,000 列，超出时失败（`catalog.too_large`），提示用"模式范围"收窄。
- 界面、绑定校验和 AI 建议都读缓存，不逐次去连数据源；界面显示上次读取的时间。
- 列的类型族决定它能绑定到什么数据类型的属性：

| 类型族 | PostgreSQL 类型 | 可以绑定的属性数据类型 |
|---|---|---|
| `string` | 字符类 | string |
| `opaque` | `uuid`、枚举类型 | string，只能做相等类的比较（见下） |
| `integer` | `smallint`、`integer`、`bigint` | integer、decimal |
| `decimal` | `numeric`、`real`、`double precision` | decimal |
| `boolean` | `boolean` | boolean |
| `date` | `date` | date、dateTime |
| `dateTime` | `timestamp`、`timestamptz` | dateTime |
| `other` | 其余（json、数组、bytea、几何等） | 不能绑定 |

- 只允许不需要转换列就能比较的组合：数值列绑到文本属性后"包含"会在数据库里报错，所以不允许。M3 不对列做类型转换（列上的转换也会让索引失效）。
- `opaque` 族（`uuid`、枚举）能当文本显示，但数据库里没有它们的"包含""开头是"，所以只给等于、不等于、属于、为空、不为空，不给大于小于这类范围比较。它们可以排序，也可以作主键列。
- 筛选和主键的值作为绑定参数时，类型由连接器按目录缓存里该列的源类型给，`query` 只传值。批次 3 用 `uuid` 主键和枚举列各写一条测试。
- 所以一个属性能用哪些运算符，由属性的数据类型和所绑列的类型族一起决定（第 7 节）。

### 5.6 样本值

- 数据源上的开关 `allowSamples`，默认关，只有 admin 能改。关着的时候，平台除了对象查询以外不读任何行数据。
- 打开后，AI 绑定建议会对候选表各读一次（`SELECT 候选列 … LIMIT 20`，在平台里去重），每列最多取 5 个不同的非空值，每个值截到 64 个字符。这些值会发给模型，也会作为证据的引文存进平台、显示在审核页；变更集对所有登录用户可读，所以这些样本值所有登录用户都看得到（第 13 节）。
- 每次读取样本都写审计（第 13 节）。界面在开关旁用 ⓘ 说明，打开时用黄色提示条写清后果。

## 6 绑定模型

### 6.1 两种做法的评估

| | A：绑定是本体元素的新种类（选定） | B：独立的 `bindings` 模块，自带表 |
|---|---|---|
| 审核入口 | 变更项的 `op`、`kind`、目标、`revision`、`temp_ref`、逐项决定、编辑、证据全部沿用，天然是同一个入口 | 模块之间不能跨模块写表，`bindings` 写不进 `ontology.change_items`，只能另建一套变更集和审核页，与"同一个审核入口"冲突；或者让 `ontology` 合并时反过来调用 `bindings`，形成循环依赖 |
| 合并 | `_Merge` 已有按引用排序、过期目标跳过、依赖项被拒时连带跳过（`changeset.dependency_skipped`）。"表的绑定被拒，列的绑定自动跳过"不用新写 | 要重写一套同样的逻辑 |
| 发布快照 | 快照就是全部在用元素，绑定自动随版本固化；回滚到旧版本时用旧版本的绑定 | 要另存一份快照，并保证两份快照同时生成 |
| 影响分析、版本对比 | 引用图和字段对比都是按元素通用的，删除对象类型时自动带上它的绑定 | 要新写跨模块的影响分析 |
| 隔离 | 风险在于所有遍历元素的代码都会看到绑定：Turtle 导出、导入时的差异、Protégé 检查、图谱、AI 助手的上下文、识别时的对齐 | 天然隔离 |
| 上一版程序 | 迁移后旧程序照常运行；一旦有了绑定数据再回退代码，旧程序读元素列表会失败 | 回退后旧程序不受已合并绑定的影响，但未决变更集里的绑定项同样会让它失败 |

选 A。B 的隔离优点可以在 A 里用一条规则拿到：读取元素的内部函数 `_elements()` **默认只返回语义种类**（对象类型、关系、属性、约束、公理），要看到绑定的地方显式要求全部种类。现有的调用点各拿哪一种：

| 拿全部种类（要改成显式要求） | 只拿语义种类（保持默认，不改） |
|---|---|
| 新建变更集 `create_change_set`、审核人编辑变更项 `_edit_problems`：绑定项的目标和引用要查得到 | 识别时的对齐 `list_alignment_elements` |
| 合并 `_apply_change_set`、发布 `publish_release` | 图谱 `get_graph`、工作版本的 Turtle 导出 `export_working_version` |
| 版本对比 `compare`、影响分析 `impact` | AI 助手给模型的上下文 `context_for` |
| 手工保存 `save_edits`：编辑绑定，以及删除元素时算级联 | 专家模式查重 `expert.py` |
| AI 助手的提议 `assistant.propose`、导入与专家模式保存整份 Turtle（`importing.py`）：差异仍只按语义种类算，但生成删除项后要用全部种类补上绑定的级联删除。导入这条路径原来没有级联，是新增的逻辑。这一行由批次 4a 做，批次 1 不动 | 导入时算差异用的当前状态 |
| 元素列表 `list_elements`：`kind` 明确写绑定种类时 | 元素列表的默认情况 |

这样导出、差异、图谱、对齐、助手的上下文不改代码也看不到绑定，并由测试守住（第 15 节）。

还考虑过折中做法 C（绑定放在 `ontology` 模块里的独立表，变更项增加第二套目标列）。它要在变更项、提议校验、审核展示、溯源里处处区分"目标是元素还是绑定"，新代码比 A 多，隔离的好处与 A 加默认过滤相同，所以没有选。

### 6.2 元素

`ontology.elements` 新增三种 `kind`，一列 `binding`（jsonb）。绑定元素没有局部名、IRI 和名称（同公理）。

| kind | 含义 | `subject_id` | 其他引用 | `binding` |
|---|---|---|---|---|
| `type_binding` | 对象类型对表或视图 | 对象类型 | 无 | `{ target: 'table', dataSourceId, schema, table, keyColumns }` |
| `property_binding` | 属性对列 | 属性 | `parent_id`：所属的类型绑定 | `{ target: 'column', column }` |
| `relation_binding` | 关系对外键或连接表 | 关系类型 | `domain_id`：起点的类型绑定；`range_id`：终点的类型绑定 | `{ target: 'join', join }` |

- `subject_id` 原来只用于公理（"这条公理说的是哪个元素"），这里沿用同一个含义：这条绑定说的是哪个元素。
- **属性绑定挂在类型绑定下面**，不直接挂在对象类型上。理由：同一个属性可以用在多个类型上（钢铁样例的 `externalId` 没有定义域，五个类型都用），所以"属性对列"必须说明是哪张表里的列；挂在类型绑定下，引用关系也就有了，表的绑定被拒绝或删除时，列的绑定跟着跳过或级联删除。
- **连接方式**（`join`）有两种：
  - `foreign_key`：`{ kind, side, columns, references }`。`side = 'source'` 表示起点表的 `columns` 指向终点表的 `references`；`side = 'target'` 相反。
  - `link_table`：`{ kind, schema, table, sourceColumns, targetColumns }`，连接表的两组列分别对应起点和终点的主键列，用于多对多。
- **唯一性**（在用的绑定之间，由部分唯一索引和合并校验同时保证）：一个对象类型一条类型绑定；一条类型绑定下一个属性一条属性绑定；同一关系、同一对起点终点一条关系绑定。
- **校验规则**（`binding_rules.py`，提议、编辑、合并、发布共用）：
  - 类型绑定：主键列 1–8 个且不重复；数据源存在且未归档。
  - 属性绑定：属性没有定义域，或定义域是所绑类型本身或它的祖先。
  - 关系绑定：起点、终点的类型与关系的定义域、值域相容（相同或是其子类型，未写定义域、值域的不限）；两条类型绑定和连接表在同一个数据源；两侧列数相等。跨数据源的关系不在 M3（`binding.cross_source`）。
  - 修改只能改 `binding`；要换所绑的元素就删除后新建。类型绑定的修改只能改主键列：换数据源或换表也要删除后新建，它下面的属性绑定和关系绑定随级联一起删除、重新建立，不会留下指向旧表列名的绑定。"删旧建新"可以放在同一个变更集里，靠第 6.3 节的合并顺序成立。
  - 提议和编辑时另外对照目录缓存：表和列存在，列的类型族与属性的数据类型相容（第 5.5 节）。合并和发布不对照目录，因为缓存可能过期；数据源后来变了，由查询报 `query.source_mismatch`。
- 约束的放宽与新增都在迁移 v0009 里；旧种类的约束只多一条 `binding IS NULL`，上一版程序写入的数据仍然满足。
- **上一版程序**：v0009 新增的非空列都带服务端默认值并回填（`evidence.kind` 默认 `document`，`releases.binding_count` 默认 0），上一版程序插入证据和发布版本时不带这些列也能成功；新增的可空列（`elements.binding`、`evidence.source`、`change_sets.token_id`）不影响它。降级时，绑定种类的元素、变更项、目录证据，以及来源为 `ai_binding`、`mcp` 的变更集先删除，再恢复原来的约束。有了绑定数据之后再回退代码，旧程序读元素列表会失败（它不认识新种类），这与 M2 加入约束和公理两个种类时的情况相同，见第 18 节第 1 条。

### 6.3 变更项与合并

- `change_items.kind` 增加三种绑定种类；`proposed`、`edited` 增加两个键：`subjectRef`、`binding`。`parentRef`、`domainRef`、`rangeRef` 对绑定种类指向类型绑定。引用可以是元素 id，也可以是同一变更集里的 `temp_ref`，所以"新建类型绑定和它下面的属性绑定"可以放在一个变更集里。
- `change_sets.source` 增加 `ai_binding`（AI 绑定建议）和 `mcp`（MCP 提议变更）。`change_sets` 增加可空的 `token_id` 列（经哪个访问令牌提交；不建外键，同 `document_id` 的做法），用于 MCP 的署名和频率限制。
- 变更项的标记增加 `key_unverified`：AI 提出的主键列没有主键或唯一约束作依据（常见于视图），审核时要人确认。
- **合并顺序**：语义元素的新建、修改、恢复 → 公理 → **绑定的删除** → 绑定的新建、修改、恢复（类型绑定先于属性绑定和关系绑定，由现有的按引用排序保证）→ 语义元素的删除。
  - 现有的合并是"新建与修改在前，删除最后"。绑定的删除要提到绑定的新建之前并先落库，否则同一个变更集里"删旧类型绑定、建新类型绑定"时，新建项会撞上唯一性而被跳过，属性绑定跟着连带跳过，最后旧的又被删掉，类型变成没有绑定；手工保存遇到跳过项会整体回滚，换表就做不成。
  - 提前不影响依赖检查：引用绑定的只有别的绑定，绑定的删除集合在绑定内部就能算闭合；语义元素的删除仍在最后，那时它们的绑定已经删掉。
  - 同一变更集里新建的绑定不能引用本变更集正在删除的类型绑定（按无效项跳过）。
- **删除**：对象类型、属性、关系还被在用的绑定引用时，删除项跳过（`changeset.has_dependents`，现有规则）。手工编辑、AI 助手、导入、专家模式生成删除项时，一并带上相应绑定的删除项（级联）。
- **证据**：`ontology.evidence` 原来只能指向资料片段。v0009 增加 `kind`（`document` / `catalog`）和 `source`（jsonb：数据源、模式、表、列、依据的种类），`document_id`、`chunk_id` 改为可空，两种证据各自的必填项由检查约束保证。目录证据的引文由确定性代码从目录缓存生成，例如 `heat_no varchar(20) NOT NULL，注释：炉次号`、`PRIMARY KEY (heat_no)`、`FOREIGN KEY (cast_no) → mes.casting_sequence(cast_no)`；样本值只在开关打开时出现。

### 6.4 发布与快照

- 快照包含绑定元素，绑定随版本固化。`releases.element_count` 只数语义元素（界面上"元素数"的含义不变），新增 `binding_count`。
- 版本的 Turtle 导出不含绑定。
- **发布校验**新增 `release.invalid_binding`：绑定引用的元素或类型绑定缺失或已删除，属性的定义域与所绑类型不再相容，关系绑定的两侧列数不等，违反唯一性。
- M3 之前发布的版本没有绑定，对这些版本查询会得到"没有绑定数据"。
- 回滚（激活旧版本）后，查询用旧版本的绑定。旧绑定指向的数据源已归档或结构已变时，查询返回明确的错误，不影响别的类型。

### 6.5 对比、影响、导入导出

- **版本对比**的级别：新增绑定为兼容；删除绑定为不兼容（依赖它的查询会失效）；`binding` 的内容变化为需确认。发布对话框现有的不兼容提示条照常计入。
- **影响分析**：对象类型、属性、关系的"被引用"里列出它们的绑定；删除确认框的级联列表里包含绑定。
- **Turtle 导出、导入、专家模式、Protégé 检查**：都只看语义种类。导入或专家模式保存整份 Turtle 时，绑定不会因为"文件里没有"而被删除。
- **元素列表接口**默认不返回绑定；另有 `GET /api/ontologies/{id}/bindings` 返回按对象类型组织好的绑定视图（含数据源名称、与目录缓存的核对结果），供类型详情使用，所有登录用户可读（第 13 节）。

## 7 查询（`query` 模块）

**针对的版本**：本体当前生效的发布版本。响应里带版本号。本体没有发布版本时返回 409 `query.no_release`；类型在该版本里没有绑定时返回 409 `query.type_not_bound`。未审核或未发布的绑定不会被用到。

**三种查询**：

| 查询 | 说明 |
|---|---|
| 按类型列表 | 筛选、排序、游标分页；每页默认 50，最多 200 |
| 对象详情 | 按类型和主键取一个对象，附它能走的关系 |
| 沿关系走一跳 | 从一个对象出发，沿某个关系的正向或反向取相关对象，同样分页 |

- **只取绑定过的列**：SELECT 的列只有主键列和属性绑定的列。表里没有绑定的列永远不会被读出来。
- **筛选**：条件之间是"并且"，最多 10 个；运算符有等于、不等于、大于小于四种、包含、开头是、属于（最多 100 个值）、为空、不为空。可用的运算符取决于属性的数据类型和所绑列的类型族（第 5.5 节），类型列表接口对每个属性给出它能用的运算符。列的类型族不在绑定里：`query` 用 `connectors` 的"取目录缓存里的一张表"接口取所绑各列的源类型和类型族（这个接口在批次 1 就实现）；缓存里已经没有这张表或这一列时返回 `query.source_mismatch`。取值的格式先在平台按类型族校验（数字、日期、`uuid` 的写法），不合法返回 422 `query.invalid_filter`，不发给数据库；枚举的取值目录缓存里没有存，不在平台校验，由连接器把数据库报的"取值不合法"（SQLSTATE 22 类）映射成 `query.invalid_filter`。
- **排序**：最多 2 个属性，再加主键列保证顺序稳定。
- **游标分页**：按排序键加主键的键集分页，不用偏移量，所以翻到很深的页也不变慢。游标是不透明的字符串，里面带版本、类型和排序方式；与当前请求不符时返回 422 `query.invalid_cursor`，生效版本已变时返回 409 `query.release_changed`，客户端从头再查。
- **走一跳**：三种连接方式都渲染成"目标表内连接一次"的一条 SELECT。正向用关系绑定的方向，反向把两侧对调。有互逆关系时，界面用互逆关系的名称显示反向。
- **来源**：每个对象都带数据源（id 与名称）、模式、表、主键列与值。
- **取值**：整数为数字（超出 2^53 时为字符串），小数为字符串（保留原精度），布尔为布尔，日期和时间为 ISO 8601 字符串。被截断的文本在 `truncated` 里列出属性。
- **不做总数**：对大表计数可能很慢，M3 的列表不返回总数，界面只有"下一页"。
- **子类型**：列出父类型时不并入子类型的对象（M3 范围外）。
- **谁能查**：所有登录用户，以及带 `objects:read` 的令牌。M3 没有行级和列级权限：一张表一旦绑定并发布，绑定过的列对平台的所有登录用户可见。这一点写进数据源和绑定的界面说明里。

**错误**：数据源连不上 `query.source_unavailable`（502）；超时 `query.timeout`（504）；表或列在数据源里已不存在 `query.source_mismatch`（409）；数据源已归档或凭据不可用 `query.source_disabled`（409）。响应里不带驱动的原始报错。

## 8 AI 绑定建议（`ai` 模块）

**入口**：数据源详情页或类型详情的"AI 建议绑定"。请求里选数据源和范围（若干张表，或若干个模式；可以再限定若干个对象类型）。一次最多 200 张表、4,000 列，超出返回 422，请用户缩小范围。

**流水线**（任务 `bindings.suggest`，沿用任务队列和 `ModelGateway`，请求记录在 `ai.binding_suggestions`，迁移 v0010）：

1. **catalog**：从目录缓存取范围内的表；取工作版本里还没有绑定的对象类型、属性、关系。已有类型绑定的类型只补它还没绑定的属性和关系。
2. **match**：一次模型调用，把对象类型对到表，给出主键列、置信度和理由。
3. **columns**：按类型分批调用模型，把属性对到列、关系对到外键或连接表。
4. **changeset**：确定性代码逐条校验，通过的生成来源为 `ai_binding` 的变更集，全部待审核。

**发给模型的内容**：
- 本体一侧：类型、属性、关系的 id、中英文名、同义词、定义（截到 200 字）、数据类型、单位、定义域、值域。
- 数据一侧：模式名、表名、表的种类与注释，列名、源类型、可空、注释，主键，外键。
- 默认**没有任何行数据**。数据源的 `allowSamples` 打开时，第 3 步才带上样本值（第 5.6 节）。
- 主机、端口、库名、用户名、凭据永远不发。

**校验与证据**：
- 模型给的 id、表、列必须在本体和目录缓存里真实存在，否则丢弃；同一元素只取第一个通过校验的建议；丢弃的条数记在请求上，界面提示"有 N 项无法采用，已忽略"。
- 主键：表有主键时直接用表的主键，不采用模型另选的列；没有主键时（如视图）采用模型的建议并打上 `key_unverified`。
- 类型族与属性的数据类型不相容的建议丢弃。
- 证据由确定性代码从目录缓存生成，不取模型的转述：列名、类型、注释、主键、外键，以及开关打开时的样本值。所以每条建议的证据都能在目录里对上。
- 置信度和理由来自模型。

**范围**：M3 只为本体里已有的元素建议绑定，不由表结构反推新的对象类型或属性。理由：反推新元素属于识别质量的范畴，应该和对齐改造（#40）用同一套实体消解，否则会产生重复元素。变更项本身支持在同一个变更集里引用新建的元素，以后要做"表里有、本体里没有的列提议为新属性"时不用改模型。

**失败**：同 M1 的网关错误码。界面提示"AI 绑定建议暂不可用，已有的绑定不受影响"，可以重试，也可以改为手工绑定。

## 9 MCP（`mcp` 模块）

### 9.1 规范要点与实现方式

2026-11-24 读过规范 2026-07-28 的这些页面：总览、变更记录、传输（Streamable HTTP）、授权、版本与兼容、`server/discover`、工具；没有读授权的子页面和 schema 原文。要点：

- 协议无状态：取消了 `initialize` 握手、协议层会话和 `Mcp-Session-Id`；每个请求在 `_meta` 里带协议版本和客户端能力。
- 服务端必须实现 `server/discover`；声明了工具能力就必须实现 `tools/list`。`ping` 已从协议里去掉。
- 传输：一个只需支持 POST 的端点；每个 POST 必须带 `MCP-Protocol-Version` 头，另有 `Mcp-Method`（所有请求）和 `Mcp-Name`（`tools/call` 等）头，头与请求体不一致返回 400；响应可以始终是 `application/json`，不必开 SSE；通知返回 202；必须校验 `Origin` 头。
- 授权是可选的（第 4 节）。

**直接在 FastAPI 里实现，不用官方 SDK。**理由：

1. 无状态之后，一个只有工具的服务端就是"一个 POST 端点、三个方法、几个请求头的校验"，代码量小，且完全在我们已有的认证、角色、审计、错误处理之内。
2. 官方 Python SDK（PyPI `mcp` 2.3.0，MIT）会带来约 8 个新的传递依赖（`jsonschema`、`opentelemetry-api`、`pyjwt[crypto]`、`sse-starlette`、`mcp-types` 等），它的认证是围绕 OAuth 资源服务器设计的，而 M3 用的是访问令牌加我们自己的角色与作用域。
3. SDK 同时服务 2025 与 2026 两个修订版，其中 2025 版的会话处理正是我们不想要的状态。

代价是不兼容只会 2025 版握手的客户端（见第 18 节第 2 条）。为了以后能换，`mcp` 模块分两层：`tools.py`（工具的名称、输入输出 schema、处理函数，不依赖传输）和 `transport.py`（HTTP 与 JSON-RPC）；改用 SDK 时只换后者。

批次 6 开工时先对照 schema 原文核实字段名与错误码（结果里的 `resultType`、头不一致与版本不支持的错误码、工具注解的名称），以原文为准。

### 9.2 端点

- `POST /mcp`（不在 `/api` 下，不进 OpenAPI 文档）；nginx 增加这一个路径的转发和限流（第 9.3 节）。GET、DELETE 返回 405。
- 只接受协议版本 `2026-07-28`；其他版本按规范返回"不支持的协议版本"并列出支持的版本。
- 方法：`server/discover`、`tools/list`、`tools/call`；未知方法按规范返回"方法不存在"。响应一律是 `application/json`。
- `Origin`：没有这个头的请求（非浏览器客户端）放行；有的话必须与平台同源或在 `OP_MCP_ALLOWED_ORIGINS` 里，否则 403。
- 认证：所有方法都要求访问令牌。没有或无效返回 401 加 `WWW-Authenticate: Bearer`；作用域或角色不足，协议层方法返回 403，工具调用返回带错误码的工具错误。
- 工具列表对所有令牌相同（规范要求不随连接变化）；没有权限的工具可以看到，调用时被拒。

### 9.3 只读工具（批次 6a）

全部针对当前生效的发布版本，结果里带版本号；本体参数可以用 id 或 key。

| 工具 | 作用 | 作用域 |
|---|---|---|
| `list_ontologies` | 列出有发布版本的本体 | `ontology:read` |
| `search_elements` | 按名称、同义词、定义、局部名搜索类型、属性、关系、约束。术语就是元素的中英文名称、同义词与定义，用这个工具查 | `ontology:read` |
| `get_element` | 读取一个元素的完整信息；对象类型附它的属性（含继承的）、出入关系、约束摘要、父子类型、是否绑定了数据 | `ontology:read` |
| `search_objects` | 按类型列出对象，筛选、排序、分页（第 7 节） | `objects:read` |
| `get_object` | 按类型和主键取一个对象 | `objects:read` |
| `get_related_objects` | 沿关系走一跳 | `objects:read` |

- 工具结果同时给结构化内容和同样内容的文本；单次结果超过 256 KB 时截断并提示缩小范围。
- 对象类工具的结果带来源（第 7 节）。本体类工具不返回表名和列名。
- 限流：nginx 对 `/mcp` 按来源 IP 和按 `Authorization` 头各限每分钟 120 次（按 IP 的那条管住没带令牌和乱试令牌的请求），超限返回 429 和固定的 problem+json（`mcp.rate_limited`），写法同登录接口的限流。这一层是 nginx 配置，不在自动化测试里。

### 9.4 提议变更工具（批次 6b）

`propose_changes`：输入本体、标题、一组操作（新建、修改、删除对象类型、关系、属性、高级公理，结构同 AI 助手的操作，最多 50 个）和每个操作的理由。

- 要求：作用域 `changes:propose`，且主人当时的角色是 editor、reviewer 或 admin。
- 校验与 AI 助手相同（002 第 10 节的 changeset 步骤）：不合法的操作丢弃并在结果里说明，删除操作补级联项。`ontology.assistant.propose` 现在把来源和标题前缀写死为助手的，并且自己调用 `create_change_set`；批次 1 给它加上来源、标题、`token_id` 三个参数，助手的行为不变。MCP 工具的输入结构由 `mcp` 自己定义，在 `mcp/tools.py` 里转成 `ontology` 的变更项（普通数据）再交给它，不依赖 `ai` 模块里助手的转换函数。
- 生成来源为 `mcp` 的变更集，标题为"MCP：{标题前 60 字}"，提交人是令牌的主人，`token_id` 记这个令牌，所有项待审核；异人审核模式下主人不能审核它。`changeset.created` 的审计现在对 AI 来源不记操作人；`mcp` 来源记令牌的主人，明细里带令牌 id（批次 1 改 `create_change_set`）。
- 不能提议绑定，也不能审核、合并、发布。
- 频率限制：每个令牌每小时最多 10 个变更集（按 `change_sets.token_id` 和创建时间数）；每个用户同时最多 20 个来源为 `mcp` 的未决变更集。超出返回工具错误 `mcp.rate_limited`。两个计数由 `ontology` 的服务接口提供，批次 1 实现。
- 工具结果返回变更集 id、采用与丢弃的条数。AI 不直接改本体这条红线不变：这个工具只能产生待审核的变更集。

## 10 R2RML 导出（批次 6c，可选）

`GET /api/releases/{id}/r2rml` 返回某个版本的绑定对应的 R2RML（Turtle）：每条类型绑定一个 `rr:TriplesMap`（逻辑表、主语模板、类），属性绑定为 `rr:column`，外键式的关系绑定为 `rr:parentTriplesMap` 加 `rr:joinCondition`，连接表式的为针对连接表的 `rr:TriplesMap`。主语模板是"类型 IRI + `/` + 逐个主键值"。文件里没有连接信息和凭据。

只作导出，给已经有 Ontop 之类工具的用户带走映射用；平台自己不解析、不执行 R2RML。

**测试用的副本**：测试镜像里只有 `backend/`，所以 `backend/tests/fixtures/connectors/steel/` 放同样的两个 SQL 文件（做法同 OWL 样例）；`seed-steel` 装载前比对两处文件是否一致。测试的"外部数据源"夹具在同一个 postgres 服务里为每个测试进程新建一个临时库并装入样例。数据库角色是整个实例共用的，而 postgres 由几个工作区、8 个测试进程共用，所以夹具建的只读账号和有写权限的账号都用带随机后缀的名字，用完连同临时库一起删除。

## 15 测试与验收

每条都要能写成测试。后端用临时库里的冶金样例作"外部数据源"，模型用假网关。

**红线的反面用例**：

| 红线 | 用例 |
|---|---|
| 外部数据源只读 | ① `connectors` 的公开接口里没有接受 SQL 文本的方法；`SelectQuery` 没有原始片段字段。② 用一个**有写权限**的账号建数据源，经连接器的连接直接执行 INSERT、UPDATE、DELETE、DDL，全部被数据库以只读事务拒绝，表内容不变。③ 记录一次完整流程（测试、读目录、读样本、三种查询）发出的全部语句，除会话设置和事务控制外都是 SELECT。④ 筛选值里放 SQL 片段（引号、分号、注释），结果只是按字面比较，表不受影响。⑤ 扫描源码：只有 `connectors` 导入数据库驱动、建立外部连接或出现 SQL 文本。⑥ 语句超过超时被取消并返回 `query.timeout`；请求取消后数据库里的语句确实被取消。⑦ 结果超过行数上限时被截断，不会全部取回。 |
| 凭据不回显 | 分两段，断言相同：特征字符串不出现在任何响应体与响应头、捕获到的全部日志、`audit.events`、`jobs.jobs` 里，`data_sources.secret` 里没有它的明文。**连接器一段**（批次 3，`test_connectors_secrets.py`）：用特征字符串作口令，走完新建、修改、测试（成功与失败）、读目录（成功与失败的任务）、归档。**全流程一段**（批次 6a，`test_m3_secret_scan.py`）：再加上 AI 建议、审核、发布、查询、MCP，另外检查 `ai.binding_suggestions`、`ontology.evidence`、发布快照。另测（批次 3）：连不上和认证失败时，用特征主机名和特征用户名断言它们不出现在响应、日志和 `jobs.error_detail` 里（驱动原文没有漏出来）；密文换到另一行解不开；轮换后旧密文能解、`rekey` 后只剩新密钥指纹；密钥不对时返回 `datasource.credential_unreadable`。 |
| 不能连平台自己的库 | 指向 `OP_DATABASE_URL` 的数据源被拒（`datasource.platform_database`）；把主机换成同一实例的 IP 或别名同样被拒；同一实例里的另一个库可以。 |
| 没审核的绑定查不到数据 | ① 绑定的变更集未决时，查询返回 `query.type_not_bound`。② 合并了但没发布，仍是 `query.type_not_bound`。③ 发布后能查到。④ 被拒绝的绑定项、因依赖被拒而跳过的属性绑定都不出现在快照里；没绑定的列不会出现在任何查询结果和发出的语句里。⑤ 回滚到没有绑定的旧版本后，查询重新返回 `query.type_not_bound`。 |
| AI 不直接改本体 | ① AI 绑定建议只产生待审核的变更集，工作版本和快照不变。② MCP 的 `propose_changes` 同样；它不能提议绑定，不能审核、合并、发布。③ 假网关返回不存在的表、列、元素 id 时，这些建议被丢弃。④ `allowSamples` 关闭时，发给模型的文本里和证据里没有任何行数据，数据源上也没有发出读样本的语句。 |
| 令牌 | ① 撤销后的下一个请求就返回 401，`/api` 和 `/mcp` 都是。② 过期、主人停用同样立刻失效。③ 库里没有令牌全文；创建之后任何接口都取不回全文。④ 枚举 OpenAPI 里的全部操作（读和写），带一个拥有全部作用域的有效令牌请求：除接口附录"令牌作用域"一列写明的白名单外，一律返回 403 `auth.token_not_allowed`；白名单里方法不是 GET 的只有对象查询的 `POST …/objects/search`（做法同 `test_route_protection.py`）。`/mcp` 不在 OpenAPI 里，单独测：不带令牌、只带有效的 Cookie 会话请求 `/mcp`，返回 401。⑤ 缺少作用域的工具调用被拒；viewer 的令牌申请不到也用不了 `changes:propose`；主人从 editor 降为 viewer 后，原有令牌的提议立刻被拒。⑥ 同时带 Cookie 和无效令牌的请求返回 401，不回退。⑦ 超过频率限制返回 `mcp.rate_limited`。 |
| 角色 | viewer 不能新建、修改、归档数据源，不能测试连接、读取或浏览目录、发起 AI 建议、编辑绑定；viewer 拿到的数据源里 `connection`、`catalog` 为空；editor 不能新建数据源、不能合并绑定的变更集；非 admin 不能用未保存的参数测试连接。每条断言 403 `auth.forbidden` 且没有副作用。角色依赖先于服务实现执行，所以其中 403 的各条在批次 1 的桩上就能测；"viewer 拿到的数据源里 `connection`、`catalog` 为空"要有实现才能测，归批次 3。 |
| 审计 | 第 13 节的每个事件都在对应动作后出现，明细里没有口令、令牌全文、筛选值。 |

**功能**：
- **连接器**：样例库的目录与预期完全一致（表、视图、列、类型族、注释、主键、外键，包括复合主键和没有主键的视图）；目录超限；模式范围。
- **绑定**：每种 kind 的校验规则与唯一性；`temp_ref` 引用；合并顺序与连带跳过；同一个变更集里换表（删旧类型绑定、建新类型绑定及其属性绑定、关系绑定），合并成功且新的属性绑定、关系绑定都指向新的类型绑定；级联删除；发布校验；对比级别；影响分析；Turtle 导出不含绑定且逐字节不变；导入和专家模式保存不产生绑定的删除项；删除已绑定元素时带上绑定的删除项；002 的往返测试不受影响；在有 M2 数据的库上迁移后，M2 的接口测试照常通过。
- **查询**：每种运算符和数据类型；排序（含空值）；键集分页走完全部行且不重不漏；三种连接方式的正向与反向一跳；复合主键；来源字段；每个错误码；版本在翻页途中变化。
- **AI 建议**：假网关按 `expected-bindings.toml` 给出建议时，生成的变更集合并发布后，快照里的绑定与 `expected-bindings.toml` 一致；主键取表的主键；`key_unverified`；类型不相容被丢弃；证据与目录一致。
- **MCP**：`server/discover`、`tools/list`、每个工具；请求头缺失或不一致、版本不支持、未知方法、`Origin` 不在允许范围、GET 的各种响应；工具结果与 `/api` 的查询结果一致。
- **端到端**（批次 6a，`test_m3_end_to_end.py`）：一条测试走完"建数据源 → 读目录 → AI 建议（假网关）→ 审核 → 发布 → 查询炉次并逐跳走到钢卷 → 用令牌经 MCP 做同样的查询"。它要等所有必做的批次都合并后才写得出来，所以归最后一个必做的批次。
- **前端**：数据源表单（口令不回显、测试结果、样本开关的提示条）、目录的各状态、绑定编辑、审核页的绑定卡片与目录证据、探索页的筛选排序翻页与逐跳、各错误状态、令牌的一次性显示与撤销，都有主要交互的测试。

**不在自动化里的**：界面走查与截图需要用户登录开发栈；nginx 对 `/mcp` 的限流；`./dev.ps1 seed-steel` 在开发栈上的运行；AI 绑定建议的真实模型效果只在主检出目录按需评测，不进门禁。

## 16 实现批次
