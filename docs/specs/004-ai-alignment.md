# 004 识别对齐改造：候选粗筛、模型判断、合并时重新对齐

- 级别：L2（AI 写入路径与审核流程）
- 关联：议题 #40（含 #36）、#39（评测地基）、#41（总计划）；[001 M1 规格](001-m1-ai-ingestion.md) 第 4、5 节
- 状态：设计已由主会话确认（2026-11-25，第 12 节）。PR 1–3 已合并；PR 4 待合并（实现说明见第 7.2、7.3 节末尾，未达标项见第 10 节末尾）；PR 5 待做。

名词：**名称**指中文名、英文名和同义词；**主名称**指中文名（任一方没有中文名时用英文名；导入的元素两者都没有时，沿用现在的做法以局部名充当）；比较前都按 `normalize` 规范化（NFKC、小写、去空白）。**待审项**指同一本体其他待审变更集里未被拒绝的新建项。

## 1 问题

"对齐"是识别流水线里判断"资料里的这个概念是不是本体里已有的那个"的环节。现在有四个问题。

**1.1 对齐靠不断追加的字符串规则。** `extraction.py` 的 `_shares_name`、`_shares_synonym`、`MIN_NAME`、新类型同名合并等规则是 #7、#28、#31、#33 一条条加上去的，每条都对着 4 份样例资料调过，#36 是下一条。名称相同不等于概念相同（转炉、电炉都叫"炼钢炉"），名称不同也不等于概念不同（钢包、盛钢桶），字符串规则两头都只能靠特例补。

**1.2 对齐只看已合并的本体。** `list_alignment_elements` 只返回工作版本里的活动元素。审核比识别慢，一次上传的几份资料实际上总是对着同一个基线识别，各自提议新建同一个概念。合并第二个变更集时出现下面的现象（都已用测试复现，见第 13 节）：

| 情形 | 现象 |
|---|---|
| 两份资料新建同一个类型，局部名相同 | 第二个新建项 `changeset.invalid_item`，挂在它上面的关系和属性连带 `changeset.dependency_skipped`，内容全部丢失 |
| 同上，局部名不同 | 本体里出现两个同名类型 |
| 两份资料给同一个已有类型各加一个同义词 | 第二个 `changeset.stale_target`，同义词丢失 |
| 两份资料提出同一条关系，局部名不同 | 本体里出现两条同名同端点的关系 |
| 两份资料的不同元素碰巧用了同一个局部名（板坯的 `thickness`、钢卷的 `thickness`） | 第二个 `changeset.invalid_item`，属性丢失 |
| 资料里出现一个此前被删除的类型 | 对齐看不到已删除元素，合并却把它的局部名算作已占用：新建项 `changeset.invalid_item`，关系连带跳过 |

评测（`ai/eval.py`）每识别完一份就全部接受再识别下一份，正好绕开这些情形，分数反映不了"一次上传多份"的真实流程。

**1.3 提示词随本体变大。** 类型阶段和关系阶段把全部已有对象类型写进每次调用。

**1.4 慢。** 开发库的调用记录（样本少）：术语阶段 125 秒、输出约 5,300 token；类型阶段 50 秒；关系阶段 111 秒、输出约 9,900 token；输入只有 1,200–4,600 token。一份样例资料三个阶段合计约 286 秒，时间主要花在输出上。评测地基给出的基线（第 10 节以它为准）是 steel 4 份资料 752 秒、输出 65,039 token，即每份约 188 秒、16,260 token。worker 一次只处理一个任务，多份资料逐份排队。

另外两处读代码时发现的同类缺陷，也已复现：已有"炉次—使用→钢包"时，新资料里的"炉次—使用→转炉"被当作已有关系悄悄丢掉（`match_known` 只比定义域和名称，不比值域），审核人看不到；关系的直接证据按物理行判断，同一句话在硬换行的文本里被拆开后关系被丢弃（第 8 节）。

## 2 目标与范围

目标：

1. 对齐由"名称粗筛候选、模型判断、确定性规则作护栏"完成，不再为个例追加字符串规则。
2. 多份资料对着同一基线识别、依次合并后：主名称相同的概念只有一个元素，其余疑似重复都摆到审核人面前，后合并的资料的内容不丢。
3. 类型阶段和关系阶段的输入有上限，不随本体规模增长。
4. 每份资料的识别耗时减半；多份资料可以同时处理。

红线（`AGENTS.md` 第 4 节）在本设计里的落点：

- AI 的写入仍然只有变更集。模型只在识别阶段被调用；合并时不调用模型。
- 合并仍然是人的动作，合并做的事就是审核人最后一次看到的合并计划：并入哪个元素、改用哪个局部名，在审核页合并前就显示出来；显示之后本体又变了、计划因此不同，合并请求会被拒绝并要求重新确认（第 5.4 节）。
- 模型判断过的对齐（无论判为同一概念还是拿不准）都是变更集里看得见、可以推翻的一项，不会被"接受全部高置信度项"顺带接受。

范围外：能力问题、从审核中学习、AI 协助审核（后面的批次）；向量检索与 embedding；关系与属性的模型判断（本轮只对对象类型做模型判断，关系和属性用确定性的键）；AI 助手和导入产生的变更集（合并规则不变）。

## 3 总览

```
parse → terms → types → resolve → relations → changeset          （识别，worker）
                          │                        │
              粗筛候选 + 一次模型判断        护栏、引用检查、证据核验
                                                     │
                                          一个待审变更集（AI 唯一的写入）
                                                     │
审核页：逐项决定；显示"将并入 X""可能与 Y 重复"   ←  合并计划（确定性，随时可算）
                                                     │
合并：按合并计划执行；与审核人看到的不一致时拒绝（409）
```

两处新东西：识别时的**实体消解**（第 4 节），合并时的**重新对齐**（第 5 节）。前者决定"这份资料里的概念是不是已有的"，可以用模型，结论记在变更项上；后者把这些结论和主名称相同的情况落实到当时的工作版本上，只用确定性规则。

## 4 实体消解

类型阶段之后、关系阶段之前增加一步 `resolve`（进度并入 `types` 步骤，不新增 `progress.step` 取值）。输入是类型阶段给出的新类型，输出是每个类型的去向。

### 4.1 候选粗筛

候选来源：工作版本里的活动对象类型；待审项里的对象类型；本次识别里排在前面的新类型。`ontology.service` 增加 `list_alignment_candidates`，在 `list_alignment_elements` 之外返回待审项（只读副本，带所在变更集的 id 与标题）和已删除的元素。已删除的对象类型不作粗筛候选、不送模型，只用于主名称相同时提出恢复和局部名查重（第 5.6 节）。

两个名称的相似度（规范化之后）：

| 情况 | 相似度 |
|---|---|
| 完全相同 | 1.0 |
| 有一方只有一个字（且不完全相同） | 0 |
| 一方包含另一方 | 0.6 + 0.4 × 短的长度 ÷ 长的长度 |
| 其他 | `difflib.SequenceMatcher` 的 ratio（标准库，兼顾字符重合与"钢包／钢水包"这类缩略） |

一对类型的得分：双方的名称两两算相似度，各乘权重后取最大。权重：主名称对主名称 1.0，主名称对同义词 0.9，同义词对同义词 0.8（英文名按主名称算）。得分不低于 0.5 的成为候选，每个新类型取得分最高的 3 个。局部名不参与（它是模型起的标识符）。不引入向量和 embedding 调用，不引入新依赖。

0.5 和 3 是初值，没有在 steel 上验证过。几个例子：转炉／氧气转炉 0.8；钢包／钢水包 0.8；钢种／钢种成分要求 0.73（是候选，模型应判不同）；转炉／电炉、钢种／钢号、炉次／转炉都是 0.5。两个字的名称只要共用一个字就是 0.5，刚好够线：这一档里同义的（钢种／钢号）和不相干的（炉次／转炉）靠字面分不开，所以都交给模型。阈值取 0.5 还是 0.6，是"多判一些候选"和"漏掉这一档同义词"之间的取舍，由 PR 3 的评测定；取 0.5 时没有得到判断的候选对会按 G5 带上标记，改写直接调用 `build_proposals` 的既有用例时要给出判断。**PR 4 定为 0.5，不改为 0.6**，理由有三：
- 收益小：`resolve` 的输出只占总输出的 1%–1.5%，改为 0.6 省下的输出可以忽略。
- 0.5–0.6 这一档目前没有同义对，模型都判对了：PR 4 第 2 次全量中，这一档的判断对 steel 23 对、maintenance 63 对，全部判为"不同"，不是同一概念的也没有被误判为相同。
- 召回会降：阈值越高，粗筛召回的下界越低，这一档里的同义词（钢种／钢号这类）会漏掉。

**粗筛的限度。** 字面上几乎没有重合的同义概念（钢包／盛钢桶只看这两个名称是 0.4）粗筛筛不出来。它们靠另外两条路进入判断：模型在类型阶段把资料里出现的别称写进同义词（提示词本来就这样要求），同义词对上主名称得 0.9；类型阶段的模型直接用已有类型的 id 提名（护栏 G3）。提名要求这个已有类型出现在类型阶段的输入里，第 6 节因此规定"不超过上限时全量给出"。本体超过上限后，资料里没出现过别称、又不在相关类型邻域里的同义概念不会被发现，只能新建且不带标记；这是不用向量检索的代价，用下面的指标跟踪。

**粗筛召回**（免费、确定性，写进评测输出）：对 `expected.toml` 每个期望组里的名称两两计分，报告成为候选的比例。它只看名称、不看模型写的同义词，是下限。

### 4.2 模型判断

- 主名称相同的候选对不送模型（护栏 G1）。没有候选的类型不送模型。剩下的候选对合成**一次**调用（`purpose = extract.resolve`，用 `OP_AI_MODEL`）；一份资料超过 40 个待判类型时每 40 个一批。没有待判的类型就不调用。
- 输入：每个待判类型的中文名、同义词、定义，和它的候选（短别名、中文名、同义词、定义、父类型的名称、至多 5 个属性或关系的名称）。待审项作为候选时同样给出。
- 输出（结构化）：`decisions: [{ type, candidate, verdict, reason }]`，每个待判类型一行；`verdict` 取 `same`（同一概念）、`different`（不同概念）、`unsure`（拿不准）；`candidate` 是它指的那个候选，全部不同时为空；`reason` 不超过 30 字。
- 提示词要点：同一概念指同一类事物的不同叫法；上下位、整体与部分、工艺与执行它的设备都不是同一概念；依据不足时答拿不准。举例用通用词，不用样例资料里的词。
- **事物与它的记录**（#57、#58 定）：按"记录是否被单独标识和跟踪"区分，类型阶段与消解阶段用同一段提示词（`prompts.RECORD_RULE`）。事件只靠它的记录来识别时（每发生一次就是一条记录），二者是同一概念，用记录的名字；主数据以事物自己的编号为键、每个事物一条时，主数据就是这个事物；记录有不同于事物的标识时（另行编号的证书、报告），是不同概念。"被单独标识和跟踪"通常表现为有自己的编号或代码，或者原文列出了每一份、每一次记录的数据；编号只是最常见的证据，不是唯一判据。
- 调用失败按其他阶段的规则处理（网关内重试，再按任务重试）。

### 4.3 护栏

确定性规则只做下面几件事，不再判断"是不是同一概念"：

| 编号 | 护栏 |
|---|---|
| G1 | 主名称相同就是同一个，不问模型，不限字数 |
| G2 | 模型的判断只对代码送出的候选对有效；没有候选的类型一律新建，输出里出现没送出的类型或候选时忽略 |
| G3 | 类型阶段的模型给新类型用了已有类型的 id（提名）：这一对本来就是候选时照常判断；不是候选时仍送去判断，但结果最多是"可能重复"，不能判为同一概念 |
| G4 | 只靠一个字的名称对上的候选，结果最多是"可能重复" |
| G5 | 没有得到判断的候选对（输出里缺这一行，或调用方没有提供判断）按拿不准处理 |
| G6 | 一个新类型最多对上一个目标；模型对它的两个候选都判同一概念时按拿不准处理，指向得分最高的 |
| G7 | 与自己的父类型或子类型不能判为同一个，按拿不准处理 |
| G8 | 只在对象类型之间判断 |

结果的去向：

| 结论 | 目标 | 变更集里的结果 |
|---|---|---|
| 主名称相同（G1） | 活动元素 | 与现在相同：不新建；有新增的同义词或定义时生成 `update`；关系和属性直接挂到该元素 |
| 主名称相同（G1） | 本次的另一个新类型 | 合并为一项：后者的同义词并入前者，找得到的引语并入证据 |
| 主名称相同（G1） | 待审项 | 在本变更集里照常新建（每个变更集都要能单独合并）；合并时按主名称并入（第 5.3 节） |
| 模型判为同一概念 | 活动元素、待审项或本次的另一个新类型 | 在本变更集里新建，并记下"与 X 是同一概念"和理由；合并计划把它并入 X（第 5 节）。审核人可以改成保持分开 |
| 拿不准（含 G3–G7） | 任一种 | 新建，加 `possible_duplicate`，记下疑似的是哪一个和理由；审核人可以改成并入（第 5.5 节） |
| 不同概念或没有候选 | — | 新建 |

PR 3 的实现说明：（1）目标是本次的另一个新类型时，"同一概念"与"可能重复"都保留为带记录的新建项（`match_item_id` 指向本变更集里那一项）；按记录并入时，合并计划把它并入那一项将新建的元素（`ItemResolution` 的 `elementId` 为空、`elementLabel` 为那一项的名称），同一变更集里解析后端点与中文名都相同的关系和属性也并入前一项，不会成为重复关系。（2）G1 对上待审项时记一条 `name` 记录指向那一项（`match_kind = name`，没有理由，界面不提供"保持分开"）：合并计划只在双方当前的主名称仍相同时认它，跟随那一项的去向——那一项按"同一概念"并入了别的名称的元素时，本项也并入那里，否则同名的类型会因工作版本里已没有这个主名称的元素而重复新建。改名使它失效，与第 5.5 节"主名称相同的两个类型没有保持分开"一致。（3）合并时"同一个"的取法按顺序：主名称相同的活动类型、本项自己的记录、记录了本项的已合并项（取最早的）；本项有自己的记录时，它的 `match_decision` 只对自己的记录算数。

模型判为同一概念时仍然新建一项而不直接改写成对已有元素的 `update`，原因有三：审核人看得到这是一次经模型判断的对齐，并能推翻它；挂在这个类型上的关系和属性引用的是这一项，审核人拒绝它时它们按现有的依赖规则一起跳过，不会悄悄挂到已有元素上；活动元素、待审项、同批新类型三种目标走同一套机制。

| 证据核验：`evidence_not_found`、置信度乘 0.5 | M1 | 保留 |
| 局部名不参与对齐 | #33 | 保留（没有中英文名的导入元素以局部名充当主名称，是 `pipeline.known_element` 现有的做法，不变） |

改造之后，`extraction.py` 里不再有判断两个名称"算不算同一个"的规则；再遇到对齐的个例，改的是粗筛参数或判断提示词，并用评测衡量，而不是加一条规则。

## 5 待审变更集之间的重复

### 5.1 三种做法

| 做法 | 说明 | 评估 |
|---|---|---|
| A 合并时重新对齐 | 合并某个变更集时，其中的新建项如果已经对应上工作版本里的元素，就并入那个元素，依赖它的引用改指过去 | 选定。不限制审核顺序；变更集各自独立；合并时只用确定性规则，结果可以在审核页提前算出来给人看 |
| B 变更集之间建立依赖 | 后识别的变更集直接引用先识别的变更集里的新建项，先合并前者才能合并后者 | 不选。审核顺序被锁死；被依赖的项一旦被拒绝，后者的引用要整体改写；同时识别的两份资料互相看不到，重复仍会出现，还是要靠 A 兜底 |
| C 基线变化后用任务重新识别对齐 | 每次合并后，后台任务把其余待审变更集对着新基线重做对齐并改写 | 不选。要改写审核人已经看过、甚至改过的项；任务没跑完时不能合并，多一套状态；重做对齐要再调模型 |

A 的代价是合并时不能用模型，只认两种确定的情况：主名称相同；识别时已经记录在变更项上的"同一概念"（模型判断的，或审核人确认的）。名称不同、识别时又互相看不到的重复，合并时不会自动并入，要靠"可能重复"标记和审核人；同时识别的资料互相看不到的缺口用写入时的补查缩小（第 7.3 节）。

### 5.2 合并计划

合并计划是一个确定性的纯函数，由 `ontology.service` 提供，入参与返回都是普通数据（不是 ORM 对象），合并、变更集详情接口和评测共用：

```python
def plan_merge(
    items: Sequence[PlanItem], elements: Sequence[PlanElement], *, base_iri: str
) -> dict[UUID, Resolution]: ...
# PlanItem：变更项当前生效的字段（审核人改过的以改后的为准）、决定、是否被审核人改过；PR 3 起加对齐记录
# PlanElement：工作版本里一个元素（含已删除的）的名称、kind、端点、状态、revision、创建时间
# Resolution：见第 9 节的 ItemResolution
# base_iri：判断"IRI 已被占用"用
```

实现在 `ontology/mergeplan.py`，经 `ontology.service.plan_merge` 提供给别的模块。

它对每个未被拒绝的项算出合并时会怎样：

| 结果 | 适用 | 条件与含义 |
|---|---|---|
| `create` | 新建项 | 下面两种都不是：照常新建 |
| `into` | 新建项 | 有一个活动元素与它是同一个（第 5.3 节）：不新建，把它的内容并入那个元素；本变更集里引用它的项改指那个元素 |
| `rename` | 新建项 | 没有同一个的元素，但局部名或 IRI 已被别的元素占用（含已删除的）：照常新建，局部名在后面加数字（规则同 `unique_name`）。同一变更集里各项要的局部名先保留给它们自己，再给改名的项挑数字。自带 IRI 的项不改名，冲突时仍是无效项 |
| `update` | 追加型更新；目标已经是活动元素的恢复项（第 5.6 节） | 只做追加；列出目标已有值、因此不会写入的字段 |

计划按引用顺序算：关系和属性的端点先按它所引用的项的结果解析成元素，再判断自己。计划只适用于 `ai_extraction` 来源的变更集；其他来源、删除等其他操作不变。PR 1 先定下这个函数的签名，PR 2 的评测场景依赖它。

函数只看得到一个变更集。对齐记录涉及别的变更集时（对方是哪个变更项、它是否已经合并成了元素、别的已合并项是否记录了本项），由调用方先查出来填进 `PlanItem`；这段解析也放在 `ontology.service` 里，合并与评测共用，不各写一份。

### 5.3 "同一个"在合并时的定义

| kind | 同一个 |
|---|---|
| 对象类型 | 主名称相同的活动对象类型；或者按对齐记录是同一概念：本项的记录指向 X，而 X 是活动元素，或 X 是已经合并成某个活动元素的变更项；或者反过来，某个已合并的项的记录指向本项（有多个时取创建最早的）。记录的有效结论这样定：双方任何一项被审核人定为保持分开，就不是同一个；否则有一方被定为并入，就是同一个；都没有决定时按记录本身（同一概念算，可能重复不算） |
| 关系 | 定义域、值域（解析之后）相同且中文名相同的活动关系 |
| 属性 | 定义域（解析之后）相同且中文名相同的活动属性 |

有多个元素满足时取创建最早的。记录的对象还是待审项、尚未合并时，本项照常新建；对方后合并时并入本项产生的元素。

并入（`into`）只做追加，不覆盖已有内容：

- 同义词合并；本项的中文名若不是目标的名称，作为同义词加入。
- 定义、英文名、属性的单位：目标为空时才填。
- 父类型：目标没有父类型、且不会成环时才设。
- 数据类型、必填、多值：不改，以已有的为准；与本项不同时列在 `keptFields` 里，审核页写明"已有元素的……保持不变"。设父类型会成环时同样不设，并列出 `parentRef`。
- 有内容变化时目标的 `revision` 加一；本项的 `applied_element_id` 记为目标，来源证据因此挂到目标上。

### 5.4 审核人看得到将要发生什么

- `GET /api/change-sets/{id}` 的每一项带 `resolution`（合并计划的结果）。审核页据此显示："合并时将并入已有的「转炉」"（写明元素名称，以及已有元素保持不变的字段）；"局部名 Converter 已被占用，合并时改用 Converter2"。这两类提示会改变合并的结果，按界面规范第 4 节用卡片上的显著标记，不藏在悬浮气泡里；模型给的理由带 ✦AI 标识。
- 详情同时返回 `resolutionToken`：对计划里所有依赖当前工作版本的条目做的摘要，包括 `into`（目标元素及其 `revision`）、`rename`（将用的局部名）、追加型更新和恢复（目标元素及其 `revision`）。目标元素在审核人看过之后有任何变化，令牌都会变。令牌不显示在页面上。
- 合并请求带上令牌。服务端在锁住本体之后重算计划，令牌与请求里的不一致时返回 409 `changeset.resolution_changed`，不做任何修改；审核页重新取详情，提示合并结果已与页面上显示的不同，各项的说明按最新情况更新，由审核人再点一次合并。请求不带令牌时，只有这次合并用不到新规则才放行：计划里没有 `into`、`rename`，没有目标 `revision` 已变的追加型更新，也没有目标已是活动元素的恢复项；否则同样返回 409 `changeset.resolution_changed`。放行时的行为与改造前完全相同，非追加型更新过期照旧跳过并报 `changeset.stale_target`。
- "接受全部高置信度项"不包含下面几类：计划不是 `create` 的新建项（包括因为挂在被并入的类型上而与已有关系、属性同键的项）；带对齐记录的项（包括记录在对方项上、合成显示的）；识别提出的恢复项。
- 模型判为同一概念的项另有一个单独、显式的批量操作（PR 3）："并入已有元素（N）"，先列出每一项将并入哪个元素，审核人确认一次后一起接受；它不并进"接受全部高置信度项"。"可能重复"的项没有批量操作，逐项决定。其余几类逐项决定。
- 合并之后的 `resolution` 反映实际发生的结果，由已有数据推出，不新增标记或列。先判并入：本项的 `applied_element_id` 指向的元素不是本项创建的，即它的创建时间严格早于本变更集的合并时间（一次合并里新建的元素与变更集的合并时间取同一个时间值，现有代码已是如此），或同一变更集里排在前面的项已指向它。不是并入的，该元素的局部名与本项的不同就是改名。合并之后 `keptFields` 为空（当时哪些字段没写已无从推出），更新项和恢复项的 `resolution` 一律为空。上一版程序读这些数据不受影响。

### 5.5 审核人对对齐的决定

带对齐记录的项在审核页显示对方是谁（已有元素，或"变更集《识别：某资料》里的某项"）和理由。记录在对方项上的（第 5.3 节"反过来"的情况：对方先识别出本项的概念并已合并）同样显示，内容由对方的记录合成。审核人的结论一律写在自己正在审的这一项上（`match_decision`），不去改对方：对方所在的变更集可能已经合并，不能再改。审核人除了接受、拒绝，可以改对齐的结论：

- **并入**（用于"可能重复"）：确认是同一概念。此后按"同一概念"处理：对方已是工作版本里的元素就并入它；还是待审项时，先合并的一方新建，后合并的一方并入。挂在本项上的关系和属性随之改指，不会像拒绝那样连带丢失。
- **保持分开**（用于"可能重复"和模型判的"同一概念"）：确认不是同一个，去掉标记，合并时照常新建。

对方那一项已经被定为保持分开时，本项只显示这个结论，不再提供"并入"（按第 5.3 节它不会生效）。

主名称相同的两个类型没有"保持分开"：确实是两个概念时，审核人改其中一个的名称，计划随之变回 `create`。

### 5.6 相关的三处修正

- **追加型更新不判过期。** 识别产生的 `update` 只加同义词、只在定义为空时补定义（`_maybe_update`）。这类项在目标的 `revision` 变化后照常应用：同义词合并；目标已有定义时不覆盖，并在 `resolution` 里列出。只限未经审核人修改、且只含同义词和中文定义的更新项；审核人改过的项是审核人对着当时的元素写的，仍按原来的规则：`revision` 变了就判 `changeset.stale_target`，没变就按所写的内容应用。目标在审核人看过之后变了，由令牌拦住（第 5.4 节）。
- **已删除的同名类型。** `list_alignment_candidates` 的返回里包含已删除的对象类型。新类型与已删除类型主名称相同时，提出 `restore`（带上要追加的同义词与定义），关系和属性引用被恢复的元素；审核页显示为"恢复"。审核人拒绝恢复时，引用它的项按现有规则连带跳过。两份资料都提出恢复同一个类型时，后合并的那个目标已经是活动的：合并计划把它算作 `update`，只做追加，不判过期或无效（这是合并一侧的改动，归 PR 1）。局部名查重同时计入已删除元素的局部名；识别之后才被删除的，由合并计划的 `rename` 兜底。恢复项不带任何字段时也算追加型：目标已活动就什么都不做、照常计为已应用；审核人改过的恢复项按原来的规则处理。
- **关系的对齐键带值域。** 见第 4.4 节。

句子编号比逐字抄写多一种失败方式：编号存在，但引错了句。它要量得出来：评测报告**证据字面核验率**（类型和属性：被引用的句子里出现该项的名称；关系：两端的名称都出现），PR 4 前后对比（第 10 节标准第 7 条）。核验不过的项怎么处理（例如按 `evidence_not_found`），由 PR 4 定并写进本节。

**核验不过的项（PR 4 定）。** 字面核验看的是模型所引的那一句，替换之前。按模型给出的项计（已有的关系、属性和没有新内容的已有类型也计入），不按提议项计；名称取该项自己的名称，对上已有类型的（主名称相同或模型用了它的 id）再加上那个类型的名称，判为同一概念、尚待合并的不加。

| 情形 | 类型 | 属性 | 关系 |
|---|---|---|---|
| 编号不存在（含没给、格式不对） | `evidence_not_found`，置信度乘 0.5，无证据 | 同左 | 丢弃（没有直接证据） |
| 那一句没有出现它的名称 | 改用文档里第一句出现它任一名称的句子，不加标记 | 同左，优先取同时出现所属类型名称的一句 | 丢弃：只按所引的那一句（或那一小段）判断，不另找 |
| 文档里没有一句出现它的名称 | 保留所引的那一句，`evidence_not_found`，置信度乘 0.5 | 同左 | — |

取舍：类型和属性不丢弃，因为它们的证据只用来给审核人看，换成第一句点名它的句子，审核人看到的仍是相关原文；全文都没出现它的名称，说明名称是模型改写的或证据靠不住，才标出来请审核人核实（标记沿用现有的 `evidence_not_found`，不新增取值）。关系的证据同时就是"直接写明"的依据，换句子等于替模型找证据，所以照旧丢弃。属性的名称比类型短、常在表头里与说法不同的名称一起出现（PR 3 的引语里只有约 57% 含属性名），这条规则会让一部分属性带上标记；评测的打分不看标记，审核时这些属性要逐项核对。

**PR 4 实测：关系的丢弃比例上升。** maintenance 顺序场景里，模型给出的关系有 21% 因所引那一句没有同时写出两端名称而被丢弃，PR 3 用逐字引语时约 12%；steel 是 1.8%，PR 3 时为 0。maintenance 被丢的 31 条里：
- 引了不存在编号的：0 条。
- 把所引句和前后各一句合起来看能写出两端名称的：5 条。这部分与"只能引一个句子单元"有关：逐字引语可以跨过被"；"切开的列表项和换行。
- 其余 26 条连同前后句也写不出类型的原名，多是简称、改写的说法或表格列名（检测报告／油液检测报告，日常点检任务／日点检任务）。

试过"所引句不含两端名称时，取同一块里最近的一句"：在能回放到的那一段只救回 1 条，而且是错的，所以没有采用。关系核验对简称过严的问题记在 #60。

**关系可以引一小段连续的句子（#58）。** 关系的 `sentence` 可以是一个编号，也可以是同一块里的一段连续编号（`3.12-3.14`），至多 3 个句子单元。提示词写明：通常引一句；引导句和列表项、表头和紧接着的一行这类要合起来才写全的，引这一小段。表头与后面第二行以后的行隔着超过 3 个单元（或分在两块）时引不到，这种情况留到 #60 再议。各单元分别规范化、拼接时互不相连，名称不会由前一单元的结尾和后一单元的开头拼成。核验与 PR 3 相同：这一段合起来写出两端的名称（任一名称）才算直接证据，否则丢弃；证据保存这一段原文的起止位置。跨块、倒序、超过 3 个单元的按编号不存在处理（丢弃）。类型和属性不变，仍引一句；给了一段的按编号不存在处理。不替模型另找句子。

`resolve` 的输出每个待判类型约 25 token，是新增的。

### 7.3 推理强度与并发

- **推理强度**：`structured` 增加可选参数 `effort`，不为空时传 `reasoning={"effort": …}`。新增配置 `OP_AI_EFFORT`（关系、`resolve` 用，默认 `low`；PR 4 起术语阶段不设强度，见第 7.2 节）和 `OP_AI_REASONING_EFFORT`（类型阶段用，默认 `default`）。取值 `default` 表示不传这个参数、用服务端的缺省，供不认这个参数的兼容服务使用（`Settings` 忽略空的环境变量，所以不能用空值表示；也不用 `none`，它是合法的强度值）。类型阶段要不要降到 `low`，由 PR 4 的评测决定。`gpt-6.2-sol` 是否接受 `reasoning.effort`、`gpt-6.2-astra` 是否接受 `low`，都没有验证过，实现前各用一次极小的真实调用确认（第 12 节）。
- **同一份资料内**：术语阶段各批之间、关系阶段各批之间互不依赖，改为同时调用，结果按批次顺序合并（输出不因并发而变）。类型阶段后面的批次要看前面的结果，保持顺序。
- **多份资料**：worker 同时处理至多 `OP_WORKER_CONCURRENCY` 个任务（默认 3，取值 1–8）；全进程同时进行的模型调用不超过 `OP_AI_MAX_CONCURRENT_CALLS`（默认 4），资料并发与批次并发共用这个上限。
  - 与任务租约的关系：领取（`FOR UPDATE SKIP LOCKED`）、心跳、租约校验都是按任务进行的，并发不改变这套协议。要注意的只有一点：同一事件循环里的纯计算（生成变更集、粗筛）会挡住别的任务的心跳，耗时可能超过几秒的放到线程里做。
  - 安全条件：第 5 节的合并时重新对齐合入之后才能开。它保证同时识别的资料即使各自新建主名称相同的概念，合并后也只有一个。名称不同的重复在同时识别时互相看不到，补救是写变更集时的**补查**：`create_change_set` 的事务先锁住本体行（写入因此排队），再用粗筛查一遍识别开始之后才出现的待审项和才进入工作版本的元素，新出现的候选对不调模型，直接按拿不准标记。补查由 `ai` 模块在调用 `create_change_set` 的同一个事务里做（先经 `ontology.service` 加锁并取候选，再写入），`ontology` 模块不反过来引用 `ai`。
  - 默认 3 的依据：Docker 主机与别的项目共用，解析子进程吃 CPU；模型侧的限流由网关重试兜底。没有实测，实测后调整。
- **PR 4 的实测与取舍**：开工前用 `./dev.ps1 ai-check`（改为对两个模型各调一次、带各自的强度）实测，`gpt-6.2-sol` 与 `gpt-6.2-astra` 都接受 `reasoning.effort = low`。转写（扫描 PDF）不设强度，用服务端缺省：它是逐字照录，不在本节的四个阶段里。`OP_AI_REASONING_EFFORT` 保持 `default`（不传）。它没有单独评测过：付费额度用在了术语阶段的诊断上。另外，第 2 次全量里类型阶段的推理 token 很少：steel 4 次调用共 350 个，maintenance 8 次调用共 571 个，降到 `low` 省不了多少。`OP_AI_EFFORT` 的默认值 `low` 用在关系和 `resolve` 上。`resolve` 的输出只占总输出的 1%–1.5%，判断全部为"不同"，与 PR 3 一致；关系阶段的输出从 PR 3 的每份约 8,300 token 降到约 2,700 token（steel）。
- **PR 5 的实现**：
  - 术语、关系各批同时发出，结果按批次顺序合并；进度按完成的批数递增。一批失败时取消其余还在进行的调用，抛出的就是那一批的错误（不是异常组），所以可重试的模型错误、租约丢失的处理与逐批调用时相同。`resolve` 通常只有一次调用，各批仍依次进行；类型阶段要看前面批次的结果，保持顺序。
  - 资料之间保持顺序：评测的两个场景照旧一份接一份识别。
  - `Extractor` 不再保存上一次运行的统计（`last`）：评测按每次运行传入自己的 `RunStats`，所以一个 worker 同时处理的几个任务可以共用一个 `Extractor`。
  - 调用上限在网关里，按每次尝试占用：等待重试的调用让出名额。一个 worker 进程只有一个网关，所以这个上限就是全进程的上限。
  - 回放的用量按调用归属：每次调用在自己的上下文里计数（`contextvars`），同时进行的调用不再互相串数。录制里每次调用的 `seconds` 包括等待名额的时间；每份资料从开始到结束的秒数另记在 `usage.elapsed`。
  - 生成变更集与消解前的粗筛放到线程里做，不挡住同时运行的其他任务的心跳。
  - worker 在停止时不再领取新任务，等手上的任务做完。任务处理函数以外的错误（例如记录结果失败）照旧让 worker 停下，但会先等其他任务做完。
  - 开发集回放：steel、maintenance 用 PR #62 第 2 次全量的录制（`recordings-tg-2`），全部命中、没有一次模型调用，两个场景的结果与 PR #62 逐项相同，各份资料、各阶段的录制用量也相同。
- **配置的传递**：`compose.yaml` 逐项透传环境变量，上面四个配置不加进去时容器里只能用代码里的默认值。PR 4、PR 5 各自把自己的配置项加进 `compose.yaml` 的 `x-api-env`（L2）。

## 8 直接证据按句判断

**现状核实。** `states_link` 取引语所在的物理行（引语跨行时取首尾两行之间的全部）。引语定位不计空白，所以模型引了整句、整句又被硬换行拆开时并不受影响；出问题的是模型只引了半句的情况：同一句话、同一条引语，不换行的文本里这一行同时有两端的名称，硬换行的文本里引语所在的那一行只剩一端，关系被丢弃。复现见 `test_relation_evidence_does_not_depend_on_where_the_lines_wrap`。反过来，Markdown 和 Word 的一行是一整段，两端只要在同一段的不同句子里就算有直接证据，比"一句话直接写明"宽。也就是说同一条规则的松紧取决于文件格式。

**改法。** 判断单位改为引语所触及的**句**（引语跨几句就取这几句）。切分规则（`ai/sentences.py`，纯函数，句子编号也用它）：

- 句末标点（。！？；!?;，以及后面是空白或结尾、前后不都是数字的英文句点）是边界。
- 空行是边界；下一行以列表、表格、标题的记号开头（`-`、`*`、`•`、`|`、`#`、数字加点或顿号）时，换行是边界：一个列表项、一个表格行各是一个单位。
- 其余的换行是否边界，看前一行是不是被排版折断的：前一行不以句末标点结尾，且显示宽度（全角字符算 2）不小于本块行宽 90 分位数的 0.8 倍，视为硬换行，不是边界；否则是边界。
- 护栏：连续拼接的几行里直到 300 字都没有出现句末标点时，放弃拼接，这几行各自按物理行算。PDF 里抽出的表格行没有句末标点、宽度又可能相近，没有这一条会被拼成一个很宽的单位。
- 一个单位超过 300 字时，在 300 字以内最近的换行或逗号处切开。

`states_link` 的其余规则不变。Markdown、Word 上规则会变严（同段不同句不再算）。按现有测试里 steel 的 9 条核心关系所在的原文逐条读过，两端都在引语所在的句内，按句判断应当仍然成立；这是阅读得出的结论，**没有运行**。实现时用回放确认准确率与召回率的变化，并增加两条测试：把这 9 条所在的原文按固定宽度硬换行后 9 条仍然全部保留；没有标点的多行表格不被拼成一个单位。

评测有两个场景，自 PR 2 起都经第 5.2 节的合并计划函数应用识别结果，`eval.py` 现在那套模拟（`accept`）删除：它把每个新建项直接当成新元素，不认并入、改名和恢复。

审核人按两种方式模拟：

- **全部接受**：不改任何对齐结论；模型判为同一概念的照计划并入，"可能重复"的照常新建。两个场景自 PR 2 起都报这一组数；准确率、召回率以它为准，与基线可比。
- **按标记处理**：自 PR 3 起报告（要用到对齐记录和"并入"，PR 3 之前没有）。"可能重复"的项，对方与它在期望清单里属于同一组时点"并入"，否则点"保持分开"；模型判为同一概念的项，对方与它不属于同一组时点"保持分开"；其余全部接受。

两个场景、每种模拟方式都报告：被跳过的项数；重复类型的组数（同一期望组里有多个类型），其中主名称相同的、带对齐记录的、没有任何标记的各多少；重复的关系数。

**同基线场景的录制。** 回放按输入内容取录制。同基线场景里第二份资料起，类型阶段和关系阶段的输入与顺序场景不同（没有前面资料合并进来的类型），顺序场景的录制用不上。所以它第一次要付费录一遍，之后才能免费回放。一次"steel 付费全量"按两个场景各跑一遍计，模型调用量约为现在的 1.5 倍（术语阶段的输入两个场景相同，只录一次）。PR 2 要给出同基线场景的两组数值作为后面的参照：已含 PR 1、未含 PR 2 规则修正时的，和 PR 2 之后的（两者用同一份录制回放）；因此需要 1 次这样的录制，除非评测地基已经提供。
