# ADR 0003：数据绑定、只读查询与对外访问（M3）

- 状态：提议（2026-11-24），待主会话确认后改为已采纳
- 关联：[规格 003](../specs/003-m3-data-binding-query.md)、[ADR 0002](0002-tech-stack.md)、议题 #41

## 背景

M3 要让本体连上真实数据并对外可用。评审时调整了范围和顺序（议题 #41"对路线图的调整"），下面记录这些取舍和理由。

## 决策

| 主题 | 决定 | 主要理由 |
|---|---|---|
| 连接器范围 | 统一连接器接口加 PostgreSQL 连接器；Oracle、Doris、TDengine、Web 连接器等有环境后再做 | 没有可实测的环境时写出来的连接器只能靠模拟测试，旧版本就是这样写了一万行却连不上真实数据库（[ADR 0001](0001-rebuild.md)）；Docker 主机的 CPU 也跑不了 Doris |
| 语句从哪里来 | 平台只执行自己从已发布的绑定生成的参数化 SELECT，不接受用户或模型写的 SQL | "外部数据源只读"是红线；不接受 SQL 文本，就不需要去判断一段 SQL 是否安全 |
| 语句怎么生成 | SQLAlchemy Core 生成语句，Inspector 做目录发现；PostgreSQL 用已有的 psycopg 3 | 方言负责标识符引用和分页，以后加别的数据库不用重写；不新增驱动依赖 |
| 连接层 | 只读会话加只读事务、语句超时、行数上限、可取消 | 与"只发 SELECT"相互独立的第二道防线 |
| 凭据 | AES-256-GCM，密钥由 `OP_SECRET_KEY` 经 HKDF-SHA256 派生，附加认证数据为数据源 id；用 `OP_SECRET_KEY_PREVIOUS` 支持轮换 | 认证加密能发现密文被改或被挪用；标准库没有认证加密，所以引入 `cryptography`（Apache-2.0 / BSD-3-Clause），已在 Docker 主机上实测，不需要 SSE4.2/AVX |
| 绑定存在哪里 | 作为本体元素的三个新种类（类型绑定、属性绑定、关系绑定），走变更集审核，随发布快照固化；内部读取元素时默认只取语义种类 | 审核、合并、过期检查、连带跳过、快照、影响分析、版本对比都已按元素实现，直接复用；默认过滤拿到了"独立存储"的隔离效果 |
| 模块依赖 | `ontology` 与 `connectors` 之间只有 ontology → connectors 一个方向；`connectors` 需要的"哪些表被绑定了"由启动时登记的函数提供，不反向导入。`query`、`ai` 照常调用 `connectors` 的服务接口 | 模块之间保持没有环，与否决"独立 bindings 模块"的理由一致 |
| 图存储与查询语言 | M3 不引入 Oxigraph 和 SPARQL。这修订了 ADR 0002"图存储：M3 起按需引入 Oxigraph"一行：按需的时点推后，到有需要 SPARQL 的功能时再评估 | 按本体浏览对象只需要"按类型列表、详情、走一跳"，直接对源库生成 SELECT 即可，数据不用搬进三元组库 |
| R2RML | 只作导出；不做通用的 R2RML 转 SQL，不引入 Ontop 和 Java | 通用的重写引擎工作量大且不是用户要的功能；导出能让已有 OBDA 工具的用户带走映射 |
| 查询针对哪个版本 | 当前生效的发布版本及其绑定 | 与"发布后才生效"的闭环一致；回滚时查询跟着回到旧绑定 |
| AI 绑定建议 | 默认只把名称、类型、注释发给模型；样本值由数据源上的开关控制，默认关；证据由确定性代码从目录生成 | 业务数据默认不出平台；证据不取模型的转述，保证每条都能在目录里对上 |
| MCP | 按 2026-07-28 规范（无状态），在 FastAPI 里直接实现，不用官方 Python SDK | 无状态后的只读工具服务端很小；SDK 带来约 8 个传递依赖和一套围绕 OAuth 与会话的结构，与我们的访问令牌、角色、审计不贴合 |
| 外部认证 | 个人访问令牌：随机、只显示一次、库里只存哈希、有前缀、作用域、过期、可撤销；`/api` 默认不接受令牌，逐条开放 | 外部智能体用不了 Cookie 加 CSRF；完整的 OAuth 2.1 授权服务器与企业 OIDC 一起放 M5 |
| MCP 的写入 | 只有"提议变更"一个写工具，产生待审核的变更集，放 M3 最后 | "AI 不直接改本体"是红线；先把只读做稳 |

## 与 MCP 规范的差距

规范的授权部分是可选的。实现它的服务端要作为 OAuth 2.1 资源服务器，提供受保护资源元数据（RFC 9728）并校验令牌受众（RFC 8707）。M3 不实现这部分，使用规范之外的静态 Bearer 令牌；只支持 OAuth 流程的客户端连不上。M5 补齐。M3 也不兼容只会 2025 修订版握手的客户端。

## 被否决的方案

- **独立的 `bindings` 模块自带表和审核**：模块之间不能跨模块写表，结果是两个审核入口，或者 `ontology` 与 `bindings` 互相调用。
- **绑定放在 `ontology` 模块里的独立表**：变更项要同时支持"目标是元素"和"目标是绑定"，提议校验、审核展示、溯源处处要分叉，新代码比复用元素表多。
- **把数据同步进三元组库再用 SPARQL 查**：多一份数据副本和一套同步，来源与时效都变得难讲清楚。
- **Ontop 做虚拟知识图谱**：功能完整，但要引入 Java 服务和通用的查询重写，M3 用不到。
- **用官方 MCP SDK**：如果以后必须兼容 2025 修订版的客户端，再换；`mcp` 模块把工具与传输分开，届时只换传输层。
- **凭据放环境变量或文件，不存库**：数据源要能在界面上由管理员新建和修改，放环境变量做不到。

## 影响

- 新增模块 `connectors`、`query`、`mcp`；`identity` 增加访问令牌；`ontology` 增加绑定种类，并先把 `service.py` 的合并与发布两部分拆到单独的文件。
- 新增依赖只有 `cryptography`。
- 绑定并发布的列，数据对平台的所有登录用户可见；行列级权限不在 M3。
- 被提议绑定或已绑定的表名、列名、注释，以及样本值开关打开时读到的样本值，随变更集对所有登录用户可见（包括被拒绝的建议）；只有浏览整个目录需要 editor 以上。
